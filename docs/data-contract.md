# Контракт данных, предсказаний и обратной связи

Дата подготовки: 25.10.2026; актуализация: 26.10.2026. Статус: **accepted / ready for docs-only PR**.

Подготовлено по разделам `docs/plans/reproducible-ml-ats/plan.md` «Данные и прикладная ML-задача», «API ранжирования», «Наблюдение, обратная связь и переобучение» и согласованному пакету T-1. Копия плана входит в документарный PR вместе с `tasks.md`/`progress.md`; исследовательское обоснование остаётся во внешних материалах диплома. Выбран инженерный синтетический корпус с `demo_only`; материализация и аудит данных выполняются в T-3. Набор данных ещё не создан. Приведённые поля описывают смысл данных, а не уже реализованный формат файла.

## Пары vacancy/resume

| Поле/содержимое | Смысл и ограничение |
|---|---|
| `vacancy_id` | Идентификатор вакансии; связывает кандидатов в группу прикладного оценивания |
| `candidate_id` | Идентификатор кандидата/резюме; сохраняется при проверке пересечений между split |
| Текст вакансии | Текст требований вакансии; API передаёт его как `vacancy.text` |
| Текст резюме | Текст кандидата; API передаёт его как `candidates[].text` |
| `relevance` | Независимая бинарная метка `{0,1}` для пары `vacancy_id, candidate_id` |

Технический аудит T-3 фиксирует происхождение идентификаторов и меток, условия использования, схему, объём, положительные метки, очистку, хеши и точный состав групп. Для выбранного синтетического корпуса версионируются код генератора и его конфигурация; размер и состав проходят предусмотренный аудит T-3. Синтетические CI/негативные фикстуры отделяются от замороженного test. Независимый реальный корпус не требуется для выполнения инженерной проверки; при его добавлении происхождение, допустимость и независимость меток проверяются отдельно. Метки генератора не выдаются за реальные независимые наблюдения.

Имена, контакты и признаки, не связанные с требованиями вакансии, не используются моделью. В технические логи и prediction-events не попадают тексты или контакты. Реальные данные и артефакты не отправляются в публичный CI.

## Разбиение без утечки

1. До обучения преобразований формируются связанные группы по идентификаторам вакансий, кандидатов и близким дубликатам текстов. Одинаковые вакансии, кандидаты и дубликаты не попадают в разные части train/validation/test.
2. При доступных датах предпочтительно временное разбиение с теми же ограничениями. Конкретные доли, правила выявления дубликатов и списки split фиксируются при допуске корпуса, а не выбираются по качеству на test.
3. Одна связная компонента или часть без положительных примеров означает непригодность корпуса для выбранной проверки. Случайное разбиение строк не используется для обхода этого ограничения.
4. `data_manifest.json` содержит источник, лицензию/условия, схему, хеш, объём, положительные метки, очистку и списки split. Test замораживается; обучение preprocessing использует только train, Optuna — validation. Регулярный gate/выпуск и переобучение не читают test и не пополняют им train.

В T-3 предусмотрены отчёт counts/duplicates/intersections, проверка хеша test и отклонение непригодного корпуса. Эти проверки пока не выполнены.

## Ранжирование и метрики

Baseline — детерминированный token-overlap/Jaccard. Согласованная обучаемая модель: TF-IDF на train, cosine TF-IDF, Jaccard токенов, `log1p` длин, отношение длин и логистическая регрессия. Использование scikit-learn согласовано; совместимость конкретной версии проверяется в T-2. Точный порядок признаков и обработка пустого словаря версионируются с моделью.

Ранжирование оценивается по полной размеченной группе вакансии с `k=min(10, размер группы)`. Основная метрика — NDCG@10, дополнительная — Recall@10; публикуются число оцениваемых/неоцениваемых групп и время расчёта. Группы без положительных меток исключаются из macro-average обеих метрик, их количество и доля показываются отдельно. Сравниваемые модели используют одинаковый набор допустимых групп. При нуле пригодных групп качество не определено; это не успешный gate. Пустые группы и ничьи проверяются в T-6; при равных scores API использует возрастание `candidate_id`.

## Prediction-event

| Поле | Содержимое |
|---|---|
| `schema_version` | Версия схемы события |
| `request_id`, `input_hash` | Идентификатор запроса и хеш канонического входа, включая `top_k` |
| `vacancy_id` | Вакансия из запроса |
| `model_version`, `release_id` | Точные версии, сформировавшие результат |
| `event_time` | Время события |
| Полный упорядоченный список | Для каждого кандидата: `candidate_id`, `score` и числовые признаки мониторинга |

Полный список сохраняется до усечения по `top_k` и успешного ответа в SQLite на постоянном volume через стандартную библиотеку Python. Ошибка записи даёт 503. Уникальность `request_id` и завершённая запись обеспечивают повтор: тот же ID и тот же хеш возвращают исходный результат с исходными версиями; другой вход с тем же ID даёт 422, включая после рестарта. Отдельный экспорт событий версионируется DVC. Staging использует отдельный временный журнал, чтобы контрольные запросы не влияли на рабочий мониторинг.

## Feedback

| Поля | Содержимое и связь |
|---|---|
| `feedback_event_id` | Идентификатор события обратной связи |
| `request_id`, `vacancy_id`, `candidate_id`, `model_version` | Обязательная ссылка на prediction-event; кандидат и версия совпадают со снимком |
| `relevance` | Независимая метка `{0,1}` |
| `event_time`, `label_source`, `label_revision` | Время, источник и ревизия разметки |

Обратная связь — отдельный версионируемый набор. Идентичный повтор `feedback_event_id` игнорируется; конфликт отвергается. Исправление получает новую `label_revision`, история сохраняется. Отчёт выбирает последнюю допущенную ревизию до своего cutoff.

В мониторинге единица группы — `request_id` и полный состав кандидатов снимка. NDCG/Recall рассчитываются только при независимых метках для каждого кандидата на cutoff. Неполные группы исключаются, покрытие показывается по парам и группам; группы без положительных меток учитываются отдельно. Непросмотренный кандидат не становится нерелевантным, prediction не становится истинной меткой. Прикладной test группируется по вакансиям, мониторинг — по снимкам запросов.

Подтверждённый сигнал при отсутствии новой одобренной версии размеченных train-данных даёт `waiting_for_labels`. Появление данных запускает обычную цепочку DVC/GX/MLflow/gate; выпуск требует самостоятельного согласования. После успешного выпуска обновляется reference manifest, история окон сохраняется.

Контракты API и двух gates связаны в [requirements.md](requirements.md); авторизация выбора синтетики и зависимостей, а также ещё не выполненные проверки — в [decisions.md](decisions.md).
