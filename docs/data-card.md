# Синтетический корпус demo-v1

Корпус предназначен для проверки воспроизводимого инженерного цикла ранжирования резюме для вакансии. `evidence_scope=demo_only`: метки не являются независимыми наблюдениями о реальном найме, а результаты не доказывают пользу системы для работодателя или кандидата.

Все записи созданы кодом проекта, без внешних резюме, имён, контактов и персональных характеристик. Владелец разрешил публикацию этой синтетики для инженерных экспериментов и CI в решениях T-1. Новая лицензия на репозиторий этим документом не назначается. Происхождение ID — счётчики генератора с пространством имён корпуса; ID не включаются в тексты признаков.

Исходный код генератора, конфигурация и тесты закреплены коммитом [`82e61b07464fedc05bbbe0ba14a804e346a1e590`](https://github.com/seregatheone/ats_mlops/commit/82e61b07464fedc05bbbe0ba14a804e346a1e590). `data_manifest.json` содержит версию `synthetic-skills-v1`, SHA256 файла `dataset.py` и канонического снимка конфигурации. Эти хеши детерминированы и не зависят от текущего Git HEAD. Точная Git-ревизия кода модели будет отдельной частью training manifest T-7.

## Состав и метки

Из словаря технических навыков выбираются 7 требований вакансии. Положительная пара содержит 5–7 требуемых навыков, отрицательная — 0–3; к текстам кандидатов добавляются 3–6 посторонних навыков. Правило метки фиксировано до split и не использует предсказания модели. Корпус намеренно упрощён: перефразирование, реальные карьерные истории и экспертные оценки в нём не представлены. Баланс фиксирован генератором, а не оценён на рынке труда.

| Часть | Строки | Вакансии | Положительные пары | Кандидатов на вакансию |
|---|---:|---:|---:|---:|
| train | 720 | 36 | 180 | 20 |
| validation | 240 | 12 | 60 | 20 |
| test | 240 | 12 | 60 | 20 |

Итого: 1 200 пар, 60 вакансий, 1 200 разных ID кандидатов. Каждая группа содержит 5 положительных и 15 отрицательных меток, поэтому `k=min(10,n)` не покрывает всю группу автоматически. Полные размеченные группы пригодны для NDCG@10 и Recall@10; число групп без положительных меток — 0 во всех частях.

## Очистка, дубликаты и split

До любого fit выполняются проверка схемы и меток `{0,1}`, ограничения ID/текстов, Unicode NFKC и схлопывание пробелов. Идентичные повторения пары удаляются; противоречивые метки пары или тексты одного ID отклоняются. Исходные записи сохраняются отдельно в `data/source.jsonl`, очищенный корпус — в `data/corpus.jsonl`; аудит повторяет очистку по source и проверяет сохранённый receipt. Для текущего корпуса удалённых строк — 0.

Связный граф объединяет пары по ID вакансии, ID кандидата, точным и близким дубликатам текстов. Сравнение глобальное, включая тексты обоих типов сущностей. Для текстов используются множества Unicode word-токенов после NFKC и `casefold`; регистр, пунктуация и порядок слов не различают дубликаты. Точные совпадения множеств и Jaccard ≥ 0,9 объединяются union-find, включая транзитивные цепочки. Это консервативное правило для данного небольшого корпуса, а не семантический детектор перефразирования. Алгоритм требует квадратичного сравнения документов и рассчитан на локальный демонстрационный объём.

Исторические компоненты получили SHA256 от отсортированных ID участников и порядок по SHA256 от `seed:component_id`. Ошибка #36 показала, что смена namespace могла переносить те же тексты между folds нового manifest. Исправленный splitter сохраняет исходные 60 folds через hash-only semantic reservation policy, а новые компоненты упорядочивает по содержимому. Подробности, совместимость старого audit и ограничения независимости моделей описаны в [semantic-reservations.md](semantic-reservations.md). Доли 60/20/20 и округление остатка в train сохранены. Временных дат у синтетики нет; ID и специальные маркеры группы не добавляются в тексты.

Получено 60 компонент, 0 точных и 0 близких дубликатов документов; пересечения ID вакансий/кандидатов/пар/компонент между частями равны 0. Независимые отрицательные фикстуры проверяют совпадения после смены регистра, пунктуации и порядка, близкие тексты на пороге, транзитивные цепочки и коллапс в одну компоненту. Корпус с менее чем 3 компонентами, пустой частью, отсутствующей меткой или непригодной группой отклоняется.

## Замороженный test и чтение частей

Test закреплён SHA256 `35a6a0fc5c379c384ccd6ba645a4673f0f508df024d34f05355a40a1c9f14d65` и хешем точного списка пар в `data_manifest.json`. Повторная генерация в тот же manifest допустима только с тем же test freeze. Изменение seed или состава test требует отдельной версии набора с новым manifest; флага обхода freeze нет.

`load_manifest(Path(...))` проверяет metadata и отсутствие пересечений списков без открытия корпуса/частей. `load_partition(Path(...), "train"|"validation")` читает и сверяет только запрошенный файл, его SHA256, ID и метки. Загрузка test требует явного `final_evaluation=True` и предназначена для одного финального оценивания E-5. Обучение, подбор параметров, gate и регулярное переобучение используют train/validation. До появления этих модулей изоляция доказана тестом загрузчика, который запрещает открывать test/прочие части.

Полный `data audit` читает все артефакты, пересчитывает граф и проверяет freeze. Он относится к допуску/восстановлению набора и финальному аудиту; запускать его внутри fit/Optuna не следует. Хеширование и проверка допуска не означают вычисление метрик на test.

## Восстановление и проверка

В чистом checkout установите окружение Python 3.11 из закреплённых T-2 зависимостей [versions.md](versions.md), затем выполните из корня проекта:

```sh
export PYTHONPATH=src
mkdir -p /tmp/new-canonical
python -m ats_mlops.cli data generate --config configs/data.json --manifest /tmp/new-canonical/data_manifest.json --output-dir /tmp/new-canonical/data
python -m ats_mlops.cli data audit --manifest /tmp/new-canonical/data_manifest.json
python -m unittest discover -s tests/unit -p test_split.py
```

Генерация schema 2 в новом каталоге воспроизводит прежние bytes частей без сети; metadata получает новую identity и policy. Исходный schema 1 не перезаписывается. Шесть исторических файлов сохранены в DVC 3.67.1; metadata находятся в [data/](../data). Их восстановление — `dvc checkout`, для remote — `dvc pull` после настройки согласованного remote.

Публикуемый [отчёт аудита](../reports/data-audit.json) фиксирует исторические counts/duplicates/intersections и хеши. Проверки T-3 до исправления #36 выполнялись в закреплённом ML-образе T-2: Python 3.11.17, 18 unit-тестов PASS; две прежние генерации давали одинаковые байты; `dvc status --json` возвращал `{}`. После удаления рабочего `test.jsonl` настоящий `dvc checkout data/test.jsonl.dvc` восстановил его с прежним SHA256. Исторический clean-clone proof также воспроизвёл прежний manifest и DVC-кеш. Новые проверки schema 2 и сохранения старых data bytes записаны отдельно в [data-reservations.json](../reports/data-reservations.json). Это инженерные свидетельства, не измерения качества найма.

Отдельная CI-синтетика задаётся [tests/fixtures/data/ci-config.json](../tests/fixtures/data/ci-config.json): seed `1707`, namespace `ci-v1`, 9 вакансий × 12 кандидатов, 108 пар. Её генерируют в временный каталог с отдельным manifest. Тест подтверждает отсутствие связей ID/текстовых дубликатов с исследовательским корпусом. CI не открывает замороженный demo-v1 test.
