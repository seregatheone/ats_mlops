# Требования к локальному ML-стенду ATS

Дата подготовки: 25.10.2026; актуализация: 26.10.2026. Статус: **accepted / ready for docs-only PR**.

Это пакет T-1 вне репозитория реализации. Пользователь подтвердил пакет и продолжение работы 26.10.2026; источники авторизации и границы делегирования перечислены в [decisions.md](decisions.md). Документ готов к переносу в docs-only PR; совместимость T-2 и данные T-3 ещё не проверены и не созданы этим пакетом.

## Задача и границы

Согласованный прикладной сценарий — ранжирование предоставленного списка резюме для одной вакансии. Сервис возвращает оценки релевантности и версии модели/выпуска. Решение о найме принимает человек; score не является вероятностью найма.

Результат реализации — локальный стенд полного цикла: данные → проверки → обучение → регистрация → модельный gate → упаковка → проверка выпуска → согласование → активный API → наблюдение и обратная связь → кандидат на переобучение. Минимальный сквозной проход после входных согласований нужен для проверки совместимости, но не завершает диплом.

В обязательный объём входят DVC, MinIO, MLflow, Great Expectations, Optuna, Airflow, BentoML, GitHub Actions, Prometheus, Grafana и Evidently. Python/scikit-learn и локальная PostgreSQL с отдельными БД/ролями Airflow/MLflow согласованы в составе пакета. Это проектные дополнения, а не результаты выбора курсовой. Выбор конкретных версий делегирован агенту; их совместимость, lockfiles и образы проверяются в T-2. Текущие установленные версии не становятся целевыми автоматически.

Feast остаётся условным расширением. Kubernetes, полный кадровый продукт, обучение LLM, новое облако, дополнительный container registry и self-hosted runner в обязательный объём не входят.

## Проверяемые требования

| ID | Требуемый результат | Предусмотренные свидетельства |
|---|---|---|
| R-1 | Для модели прослеживаются код, данные, признаки, параметры, окружение, проверки и выпуск | Полный manifest; три независимых принудительных пересчёта |
| R-2 | Данные с нарушением контракта блокируются до обучения | Негативные фикстуры и отчёт Great Expectations |
| R-3 | Обучение, подбор параметров и регистрация экспериментов выполняются повторяемо | DVC DAG, Airflow DAG, MLflow runs и Optuna study |
| R-4 | BentoML возвращает воспроизводимое ранжирование и точную версию модели | Контракт API; контрольные запросы из отдельного окружения |
| R-5 | Выпуск требует проверенного артефакта; неудачный выпуск восстанавливает предыдущую версию | Журнал переходов; тесты отказа и отката |
| R-6 | Наблюдение отличает дрейф от измеренного изменения качества; переобучение проходит те же проверки | Отчёты Evidently; независимая обратная связь; сценарии переобучения |
| R-7 | Изменения кода проверяются GitHub Actions в изолированном контуре | Реальные успешный run и ожидаемый отрицательный run |
| R-8 | Диплом содержит воспроизводимые измерения, исходные результаты и ограничения | Протокол; CSV/JSON; графики; инструкция демонстрации |

Точное соответствие R-1–R-8 задачам, acceptance и команды check остаются в исходном `tasks.md`. Этот черновик их не заменяет и не добавляет новый критерий завершения.

## Данные, API и выпуск

[data-contract.md](data-contract.md) задаёт контракты пар vacancy/resume, split, prediction-events и feedback. Для инженерного цикла выбран публикуемый синтетический размеченный корпус с `evidence_scope=demo_only`; его генерация, manifest и split выполняются в T-3. Независимый реальный корпус для инженерных выводов не обязателен. При его появлении требуется отдельная проверка происхождения, допустимости и независимости меток; его название и размер сейчас не установлены. CI использует отдельные публикуемые синтетические фикстуры. Результаты на синтетике не доказывают пользу для реального найма.

Контракт API сохраняется из раздела «API ранжирования» исходного плана:

- `POST /rank`: `request_id`, одна вакансия `{id, text}`, кандидаты `[{id, text}]`, `top_k`; ответ содержит упорядоченные `{candidate_id, score}`, `model_version`, `release_id`, `request_id`.
- До 100 кандидатов, до 10 000 символов в тексте каждого объекта и до 1 MiB на запрос. `top_k` — 1–100; размер ответа ограничен размером списка. Пустой список даёт пустую выдачу. При равных scores порядок определяется возрастанием `candidate_id`.
- Пустой текст, повтор ID и неверный `top_k` дают 422; превышение размера — 413; отсутствие модели или невозможность сохранить prediction-event — 503.
- `POST /metadata` сообщает версии и готовность без обучающих данных и секретов. Успешная запись полного prediction-event предшествует усечению ответа по `top_k`. Идемпотентность `request_id` сохраняется после рестарта.

Модельный gate T-11 оценивает candidate, baseline и incumbent на одном validation manifest. Допустимое снижение NDCG@10 — не более 0,005; неполная lineage, нечисловые/бесконечные scores или отсутствие пригодных меток не дают успешной проверки. `outcome=passed|rejected` отделён от `evidence_scope=demo_only|independently_labeled`. `rejected` блокирует выпуск при любом scope.

Далее сохраняется последовательность: модельный gate → упаковка точной model version → неизменяемый `release_manifest.json` → `release_check_report.json` → отдельный `approval_receipt.json` → активация. Проверка выпуска подтверждает API, версии/хеши и автономность контейнера. Manifest не содержит будущего отчёта или согласования, поэтому цикл хешей не возникает. `approve` и `activate` под блокировкой проверяют incumbent; устаревший gate требует повторной проверки и новой ревизии выпуска. Для локальных demo releases после готовых проверок и staging агент может оформить согласование конкретного release ID как оператор по делегированной политике. Квитанция указывает агента и источник делегирования; подпись пользователя не имитируется. Это полномочие ограничено локальной демонстрацией и не является разрешением на production-выпуск.

Полные переходы, reconcile, откат, политика мониторинга и восемь итоговых сценариев приёмки сохраняются в разделах исходного плана «Проверка кандидата, выпуск и откат», «Наблюдение, обратная связь и переобучение», «Итоговые сценарии приёмки». Эксперименты изложены в [experiment-protocol.md](experiment-protocol.md).

## Происхождение требований

Технический источник — `docs/plans/reproducible-ml-ats/plan.md`; задачи и проверки — соседний `tasks.md`, прогресс — `progress.md`. Копии этих трёх файлов включаются в документарный PR и доступны в репозитории по указанным относительным путям. Исходные исследовательские материалы и корневой «Промпт реализации диплома.md» остаются во внешней папке диплома; промпт с локальными абсолютными путями не публикуется. Его обязательные входные согласования и их разрешение перенесены в [decisions.md](decisions.md). Измеренное исходное состояние взято из внешнего `docs/execution/T-1-proposal.md`; эти наблюдения не считаются результатом T-2.

DOCX курсовой сравнивает готовые архитектуры, расширенные заметки — инструменты четырнадцати классов. Общее ядро и дополнительные инструменты должны иметь раздельное обоснование. Нельзя приписывать DOCX выбор всего расширенного стека или считать экспертные оценки ELECTRE II измерениями стенда.
