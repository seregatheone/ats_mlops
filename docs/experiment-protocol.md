# Протокол экспериментов E-1–E-5

Дата подготовки: 25.10.2026; актуализация: 26.10.2026. Статус: **accepted / ready for docs-only PR**; статус измерений E-1–E-5: **not_run**.

Источник — разделы `docs/plans/reproducible-ml-ats/plan.md` «Воспроизводимость и manifest», «План экспериментов» и задачи T-18/T-19 в соседнем `tasks.md`. Копии плана, задач и прогресса входят в документарный PR и доступны в репозитории. Исходное исследовательское обоснование и корневой промпт реализации остаются во внешней папке; промпт с абсолютными путями не публикуется. Протокол не сокращает исходный объём. Окончательные версии, thresholds, входы и ресурсы замораживаются в T-18 до T-19.

## Входные условия и область свидетельств

Входной пакет T-1 согласован 26.10.2026; проверка совместимости T-2 ещё не выполнена. На 25.10.2026 аудит в `T-1-proposal.md` сообщает платформу arm64 и лимит Docker VM около 7,75 GiB RAM. Это исходное наблюдение, а не подтверждение вместимости стека. Доступные ресурсы и потребление проверяются в T-2/T-4; конкретные версии образов, Python и lockfiles выбирает и проверяет агент в рамках делегированных инженерных решений.

Для инженерного цикла согласован публикуемый синтетический размеченный корпус с `evidence_scope=demo_only`; генерация, manifest и достаточность групп ещё подлежат проверке T-3. E-5 называется проверкой на синтетическом корпусе; утверждения об эффективности реального найма исключаются. Независимый реальный корпус для инженерных выводов необязателен. Его наличие либо отсутствие отдельно отражается в T-18; метки генератора не считаются независимыми реальными метками.

Каждый запуск связывается с Git SHA, data/DVC/split hash, версией признаков, параметрами, seed, платформой, Python, lockfile hash, image ID, MLflow run/model version и хешами артефактов/отчётов. Времена, run ID и другие служебные поля исключаются из сравнения детерминированного содержимого. Исходные CSV/JSON, manifests, логи, конфигурации и код графиков сохраняются, включая неудачные и отрицательные прогоны.

## Дизайн и повторы

| ID | Дизайн и количество | Что фиксируется |
|---|---|---|
| E-1 | **Три** независимых обучения в свежих каталогах на одной платформе/образе, с одинаковыми данными, параметрами, seed и ограничением потоков. После получения входов — `dvc repro -f --no-run-cache` | Хеши подготовленных данных/признаков, ранги, отклонения scores/метрик, доля успешных запусков; восстановление готового артефакта проверяется отдельно |
| E-2 | **Пять пар** прогонов одной версии данных и модели: реальный оператор вручную запускает те же CLI по инструкции, парный автоматизированный запуск выполняет Airflow | Wall-clock, активное время оператора, число ручных действий, ошибки; медиана и разброс; setup/прогрев отдельно |
| E-3 | **Не менее трёх повторов каждого** из шести сценариев: битые данные, недоступный MinIO, неполный артефакт, плохой кандидат, неготовый контейнер, сбой между переключением и alias | Блокировка ошибочного выпуска, время обнаружения/восстановления, конечная согласованность версий |
| E-4 | Контрольное окно и заранее описанные возмущения признаков; отдельные случаи «меток нет» и «метки появились», ложные и повторные сигналы. Число повторов исходным планом не задано | Обнаружение и ложные срабатывания в заданных сценариях, покрытие метками, одна заявка и прохождение повторного цикла |
| E-5 | Baseline и замороженная ML-модель на одном test после подбора; **однократный** запуск test-оценивания | NDCG@10, Recall@10, число вакансий/кандидатов, задержка; bootstrap по группам при достаточном числе групп |

В E-1 численные предсказания сравниваются с `atol=1e-6`, `rtol=1e-5`; бинарное равенство сериализованных моделей не требуется. Воспроизводимость финального обучения с выбранными параметрами отделяется от воспроизводимости поиска Optuna. Два пересчёта T-9 не заменяют требование трёх независимых пересчётов E-1.

В E-2 порядок manual/auto чередуется, входные версии одинаковы, состояние кешей контролируется, HPO отключён. Wall-clock и журнал действий оператора ведутся отдельно. Один инженер, знакомый со стендом, — ограничение внешней валидности. Скрипт не может выдать себя за ручные действия человека. Процедура готовится без повторного запроса решения; до появления реальных человеческих измерений ручная часть E-2 имеет статус `not_run`. Это не разрешает сократить пять пар или заменить их агентскими прогонами. Выигрыш по общему времени не обещается; отрицательный результат сохраняется.

В E-4 применяются настройки плана: не менее 200 пар и 10 вакансий в окне, нарушение drift threshold два окна подряд, cooldown 24 часа, одна задача переобучения одновременно. Конкретные drift tests и thresholds выбираются на калибровочной части в T-16 и фиксируются до T-19. Для проверок используются управляемые часы. Без новой одобренной версии train-меток ожидается `waiting_for_labels`; действующая модель продолжает работать. С появлением меток повторный цикл проходит обычные gates и согласование выпуска.

В E-5 используются [правила групп и метрик](data-contract.md): общие пригодные группы, macro-average, явный учёт групп без положительных меток и неопределённости при отсутствии пригодных групп. Test не участвует в preprocessing fit, HPO, регулярном gate и переобучении. Конкретное число bootstrap-выборок планом не установлено; его нельзя представлять уже согласованным или выполненным.

## Приёмка и интерпретация

До измерений T-18 требует отчёты по восьми итоговым сценариям исходного плана и отсутствие открытых дефектов, препятствующих R-1–R-8. Проверяются неполные артефакты, I/O-сбой, плохой кандидат, crash переключения и повтор триггера; версии/thresholds/ресурсы замораживаются. Точные acceptance/check сохраняются в `tasks.md`.

Реальные успешный и ожидаемый отрицательный GitHub Actions runs относятся к T-14. Локальная проверка не является доказательством состоявшегося CI. Согласование каждого конкретного выпуска оформляет оператор после gate, release check и staging. Для локальной демонстрации агент вправе выступить оператором по делегированной политике, указав себя и источник делегирования в квитанции. Подпись пользователя не имитируется; production-разрешение из этой политики не следует.

E-1/E-3 характеризуют эту реализацию на указанной платформе и не доказывают превосходство стека над всеми альтернативами. Экспертные оценки курсовой не заменяют измерения. Каждый количественный вывод диплома связывается с исходным отчётом; ограничения данных, одного оператора и одной платформы указываются рядом с выводами.

Авторизация входных решений и ещё не выполненные проверки/условия заморозки перечислены в [decisions.md](decisions.md).
